# V0.2.153 更新说明

> 回答你报的：「**为什么我点击构建后，目标卡里的东西会变**」。

## 一、真因：自动英文类名「按行号」算，而「目标卡」存的是**类名字符串**

工具里没填英文类名的卡，类名是按**它在列表里的行号**自动拼出来的：

```
普通卡列表第 3 张  →  SevenCard3      （诅咒 / 先古卡各自一套前缀，也各自从 1 数）
```

而效果里那些「指着某张卡」的地方（**目标卡**、**转化为先古卡的类名清单**、**上传的卡面**、
锻造图里的**目标卡**字段）存的正是**这个字符串**。所以：

1. 你先在「目标卡」里选了一张卡 → 存下当时那个名字（例：`SevenCard3`）；
2. 之后你又**增删 / 拖动过卡牌** → 行号一变，后面那些自动类名集体改号；
3. **改号的那一刻，引用没有跟着搬** → 那个字符串落到了**同名的另一张卡**身上
   （现在第 3 行是别的卡了）；
4. 你点「构建」时工具才去「固定类名」（把留空的类名按当前行号写实）——那时引用里存的还是旧名字，
   已经对不上你想选的那张卡了 → 你看到的就是**「目标卡里的东西变了」**。

自检里能把这件事复现出来：3 张卡、目标卡指向第 3 张（`SevenCard3`），在中间插一张之后，
**老名字 `SevenCard3` 现在的主人变成了「挪卡2」** —— 这就是你看到的现象。

## 二、修法：改号和引用**在同一拍里**搬

生成端本来就有这一步（`NameStabilizer.RenumberCardNames` → `RepairCardClassReferences`：
把「旧类名 → 新类名」的映射算出来，然后把效果里的目标卡、先古卡清单、上传的卡面、
锻造图字段一起改过去）。问题只在于**时机**：以前它只在生成（构建）时对**快照**做，
界面里那份配置没同步、而且等到构建时旧名字已经丢了。

这一版把它接到三个地方：

1. **界面每次重算候选表时先搬一次**（`RefreshCardChoices` → `SyncCardClassReferences`）——
   = 增删 / 拖动 / 复制 / 撤回 / 改名之后立刻同步，所以**不用等到构建**，
   你在界面上看到的目标卡始终是同一张卡（只是它后面的编号会跟着变）；
2. **构建时「先搬再冻」**（`NameStabilizer.Stabilize`：`RepairReferences` → `RenumberCardNames` → `Freeze`）——
   冻结出来的显式类名和引用里的名字对得上；
3. **`Naming.RenumberCardClassNames` 补上「没填类名的卡」的旧名映射**：
   以前这一支只更新「这是第几号」，不产出映射，所以那些**最常见**的（类名留空的）卡一改号就没法搬。
   现在按 `LastAutoOrdinal`（这张卡上一次的号）算出旧名 → 产出 `旧名 → 新名` → 引用跟着走。
   ⚠ 这个字段是 `[JsonIgnore]`（不写存档），所以界面每次刷新候选表时都会被写实一次 ——
   载入存档就会刷一次，因此你打开存档再动列表也是准的。

搬过什么都会写进「构建 · 日志」（只有真的搬了才写，平时不打扰）。

## 三、验证

- `dotnet build Sts2CharForge.sln -c Debug` → **0 错误**；
- `--uicheck`：Debug **3434 PASS / 0 FAIL**（V0.2.152 是 3431，新增 3 条）：
  ① 插一张卡之后「目标卡」引用跟着搬到同一张卡上；② **反向**断言老名字现在属于另一张卡
  （把你看到的现象钉住）；③ 构建（`Stabilize` → 冻类名）那条路也对得上；
- **反向验证**：把第 ③ 处修复临时关掉 → 这 3 条立刻 FAIL（引用停在 `SevenCard3`，而它现在属于「挪卡2」），
  打开即 0 FAIL；
- **默认输出不变（红线①）**：`--samplegen` 与 V0.2.143 基线 **111 个文件逐字节一致**（只差 `ExampleMod.sln` 的随机 GUID）。
