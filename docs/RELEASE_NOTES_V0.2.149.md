# V0.2.149 更新说明

> 回答你报的：「**升级后的费用怎么没效果了，比如原本 1 费，升级后 X 费，实际上升级还是 1 费**」。
> 结论：**这不是这一版改坏的，是本体（游戏）本来就不支持**——「升级时把数字费用变成 X 费」做不到。
> 这一版把工具那句含糊的警告改成**说清原因 + 给出能做到的写法**。

## 一、为什么「升级后 X 费」没效果

本体里「X 费」不是一个数字，而是卡牌上的**一个开关**：`CardEnergyCost.CostsX`
（打出去时会花光所有能量、效果按花掉的量算）。它是在**第一次读这张牌的 `EnergyCost` 时**、
由 `HasEnergyCostX` 捕获下来**定死**的：

```csharp
// CardModel.EnergyCost
_energyCost ??= new CardEnergyCost(this, CanonicalEnergyCost, HasEnergyCostX);   // X 与否在这里定死
// CardEnergyCost 构造函数
Canonical = ((!CostsX) ? canonicalCost : 0);
```

之后打出、扣费、`ResolveEnergyXValue()` 全都只看这个**缓存下来的布尔值**。而升级能改的只有**数字**：
`EnergyCost.UpgradeBy(差值)`（也就是工具一直生成的 `OnUpgrade()` 那一行）。
所以：

- 「1 费 → 升级后 X 费」：**做不到**（X 那一档改不了）；
- 反过来「X 费 → 升级后固定 2 费」：**也做不到**（本体遇到 X 费牌直接返回）；
- 能改的只有「2 费 → 升级后 1 费 / 0 费」这种**数字到数字**；
- 以及「一开始就是 X 费，升级后 X 多 N」（`x = ResolveEnergyXValue() + (base.IsUpgraded ? N : 0)`）。

以前工具对「1 费 + 升级后费用填 X」只给了句很含糊的警告（「X 会被当成 0，这一段等于不生效」），
所以看起来像「工具没生成 = 坏了」。现在的警告写清了：

> 卡牌「…」的「升级后费用」写的是 X，但这张牌现在的费用不是 X —— **本体做不到「升级后把数字费用变成 X 费」**：
> X 是卡牌构造时定死的一档（`CardEnergyCost.CostsX` 在第一次读 `EnergyCost` 时就捕获了，之后打出 / 扣费 / 取值全看它），
> 升级能改的只有数字（`EnergyCost.UpgradeBy`）。所以这一段不会生效，升级后还是原来的费用。
> 能做到的两种写法：① 想要「X 费」就把「费用」框一开始就填 X，再在「升级后费用」里写 X+1（= 升级后 X 多 1）；
> ② 想「升级后更便宜」就在这一栏填数字（例：1 费 → 升级后 0 费）。

「升级后额外资源量费用」那一栏同理（`HasStarCostX` 也是同一套机制），警告也换成了同样的说法。

## 三、如果你确实想要「升级后变 X 费」

可以做一次**实验性**尝试（用 `HasEnergyCostX => base.IsUpgraded` 这种条件覆写），但有两个已知风险，
需要你进游戏实测：

1. X 与否是**第一次读 `EnergyCost` 时**捕获的 —— 牌组 / 奖励界面先读过它的话，那张牌就定死成非 X，
   界面上可能仍显示原来的费用（战斗里的牌是另建的实例，有可能拿到 X）；
2. 效果里的 X 取值（`ResolveEnergyXValue()`）也要跟着改成「升级后才读」，否则效果会按 0 算。

工具现在的默认行为是**不生成 + 报警告**（宁可不生效也不要静默生成半截）。你说要做我就做一版给你实测。
